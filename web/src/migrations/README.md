# Миграции БД (Payload)

> ⚠️ **Правило: `.ts` + `.sql` + `.json` коммитятся ВСЕГДА вместе.** `.json` — это
> drizzle-снапшот схемы, против которого генерируется следующая миграция.
> Снапшота нет → «текущее состояние» считается пустым → `migrate:create` выдаёт не
> инкремент, а полную схему с `DROP TABLE … CASCADE` в `down()`. Файл при этом валиден
> и выглядит правдоподобно: ловится только чтением глазами. Поэтому **`down()` перед
> применением читать глазами всегда** ([G192](../../../../brain_matrica/cross-project-ideas/GOTCHAS.md#g192)).

Подход зеркалит SabantuyMalmyzh: каждая миграция — пара файлов с одинаковым именем:

- `<ts>_<name>.ts` — стандартная Payload-миграция (`up`/`down` через `db.execute(sql\`…\`)`),
  регистрируется в `index.ts`. Используется командой `payload migrate`.
- `<ts>_<name>.sql` — зеркальный чистый SQL того же `up()`. Нужен для ручного
  применения на проде через workflow `apply-migration.yml` (psql -f), т.к.
  `payload migrate` в CI/standalone недоступен/висит (drizzle push prompt).

## Начальная миграция

`20260621_145321_initial.{ts,sql,json}` — полная начальная схема каркаса
(коллекции pages/posts/media/users + версии, глобалы home/header/footer,
системные таблицы Payload). Сгенерирована локально (`pnpm migrate:create initial`)
против локального Postgres; `.sql` извлечён из `up()` и проверен `psql -f` на
чистой БД (создаёт 18 таблиц, exit 0).

`.json`-снапшот к ней снят задним числом 2026-08-31 на раннере с эфемерным Postgres
(`payload migrate:create` требует живую БД, локально её нет). Что он именно к этой
миграции, а не к уехавшему вперёд конфигу, проверено фактом: сгенерированная полная
схема совпала с `20260621_145321_initial.ts` **байт-в-байт** — значит конфиг с 21.06
не дрейфовал. В снапшоте `prevId` — нулевой UUID, то есть он первый в цепочке;
18 таблиц сходится с проверкой `psql -f` выше.

## `20260831_175113_institutions` — дома культуры района

Коллекция `institutions` (+ версии), связь `posts.institution` и поле `posts.type`
(новость/афиша). Первая миграция, сгенерированная **поверх** снапшота: правило про
`.json` сразу окупилось — `migrate:create` выдал настоящий инкремент, а `down()`
дропает только новые объекты, без `DROP TABLE posts CASCADE`.

`.sql` не переписывался руками, а **извлечён из тела `up()`** — ручная транскрипция и
есть тот шаг, на котором у соседа потерялись `version_*`-колонки (G231). Что зеркало
полное, проверено фактом: на чистой БД накатаны оба `.sql` прод-путём, после чего
`payload migrate:create` ответил «No schema changes detected» — схема из `.sql`
совпадает с той, которую ждёт конфиг.

Мутационная приёмка (внесена и откачена): из `.sql` убрана строка
`ALTER TABLE "_posts_v" ADD COLUMN "version_type"` — SQL применяется чисто, шаги
сида 1–3 проходят, и падает шаг 4 с `столбец "version_type" в таблице "_posts_v"
не существует`. Это буквальная сигнатура G231, и гейт её видит.

## `20260831_184647_vk_import` — импорт из ВКонтакте

`posts`: `vk_uid` (уникальный), `source`, таблицы галереи `posts_gallery` и её
versions-двойник. `institutions`: `vk_group_id` переименован в `vk_owner_id` —
у VK owner_id сообщества ОТРИЦАТЕЛЬНЫЙ, и имя со словом «group» толкало бы
хранить число без знака.

Переименование, а не drop+create: `migrate:create` спрашивает про это
интерактивно, и ответ «rename column» виден в `up()` как `RENAME COLUMN`. Данных
в колонке ещё нигде нет (миграция `institutions` на прод не накатывалась), но
инкремент от этого честнее читается.

`.sql` снова извлечён из тела `up()`, а не переписан. Проверка та же: обе
предыдущие плюс эта накатаны прод-путём на чистой БД, после чего
`payload migrate:create` ответил «No schema changes detected».

Дедупликация импорта держится на `unique` у одного поля `vk_uid` (формат
`owner_post`), а НЕ на составном индексе по (учреждение, id записи). Составной
пришлось бы дописывать в `.sql` руками, и следующий `migrate:create` предложил
бы его снести — ловушка для того, кто станет генерировать миграцию после нас.

## `20260901_063625_vk_sources` — несколько сообществ на учреждение

`institutions.vk_group_url` / `vk_owner_id` заменены массивом `vk_sources`
(таблицы `institutions_vk_sources` и её versions-двойник). Причина не
архитектурная, а фактическая: РЦКД печатает новости и в группе, и на личной
странице, а у пяти сельских ДК рядом с действующей страницей живёт прежняя с
архивом. Решение владельца 01.09 — забирать всё.

Старые колонки миграция ДРОПАЕТ. Это безопасно ровно потому, что каталог на
прод ещё не заводился: таблица `institutions` там пустая. Заводись он раньше —
понадобился бы перенос значений в новую таблицу, а не drop.

`.sql` снова извлечён из `up()`; проверка прежняя — четыре миграции прод-путём
на чистой БД, затем `payload migrate:create` отвечает «No schema changes
detected».

## `20260904_195445_kalinino` — поглощение Калинино (D-074)

`posts`: колонка `source_url` (провенанс) и таблица массива `posts_videos` с
versions-двойником — два поля, которые есть у Калинино и которых не было у
портала: перенос без них терял бы видео и ссылку на оригинал молча (условие
Мозга 04.09). `institutions`: колонка `theme` (enum, пока одно значение
`kalinino`) — визуальный образ раздела по пути, не по Host.

Новой коллекции нет, поэтому `payload_locked_documents_rels` не меняется —
дрейф-проба G231 в деплое должна ответить «5 = 5».

Сгенерирована **на раннере** воркфлоу `migrate-create.yml` (локально Postgres
нет): существующие `.sql` накатаны прод-путём, затем `payload migrate:create`.
`.sql` извлечён из `up()` тем же воркфлоу, не переписан. `down()` прочитан
глазами: дропает только новые таблицы, колонки и типы.

## Что делает brain на ПЕРВОМ деплое

Вариант A (рекомендуемый, как в кластере) — применить SQL вручную до деплоя кода:

```bash
psql "$DATABASE_URI" -v ON_ERROR_STOP=1 -f web/src/migrations/20260621_145321_initial.sql
# затем зарегистрировать в реестре, чтобы payload migrate не пытался применить повторно:
psql "$DATABASE_URI" -c "INSERT INTO payload_migrations (name, batch) VALUES ('20260621_145321_initial', 1);"
```

Либо через workflow `apply-migration.yml` (input migration = `20260621_145321_initial`),
затем штатный деплой через `workflow_dispatch`.

Вариант B — дать Payload применить миграцию самому: на боксе с доступом к БД
`pnpm -C web migrate` (нужен payload CLI и DATABASE_URI). На проде стандартный
standalone-бандл CLI не несёт, поэтому в кластере используют вариант A.

> Примечание: `db-postgres` собран с `push: true` (dev-автосинхро схемы). На проде
> схему фиксируем миграцией (вариант A) — push на проде не запускается.
