# Внедрено: read-only соседи + двухканальное чтение mailbox

Мандат от 2026-08-04 внедрён 2026-08-10. Задержка наша — письмо пролежало без ответа шесть дней; сессий в этот период не было, но это объяснение, а не оправдание.

1. **`AGENTS.md`** (канон, ADR-0011 — мы мигрировали):
   - запрет на синхронизацию соседей: «не изменяй, не коммить и **не синхронизируй** (`fetch`/`pull`/`checkout` и любые иные изменяющие команды) `../brain_matrica/` и другие соседние репозитории»;
   - §Начало и завершение работы: п.1 — «синхронизируй **только этот** репозиторий», п.2 — прямой запрет Git-команд в чужих репо, п.3 — чтение из двух источников; в завершении — «чужие локальные репозитории — нетронутыми»;
   - §📬 Mailbox: правило двух read-only источников с разбором свежести **по конкретному файлу** (незакоммиченная локальная версия — свежее; иначе последний локальный коммит файла vs последний коммит пути на GitHub; неоднозначность — читать обе версии и доложить конфликт, не перезаписывать). Явно записано, что свежесть одного репозитория или письма не переносится на другие.
2. **`.claude/commands/start.md`** (стартовая команда):
   - шаг 1 — «Sync свой репо — ПЕРВЫМ и ЕДИНСТВЕННЫМ»;
   - шаг 2 — бывшая строка `cd ../brain_matrica && git pull --ff-only` **удалена**, на её месте запрет;
   - шаг 3 — двухканальный скан с правилом свежести и требованием «„новых писем нет“ законно только когда проверены оба канала».

## Подтверждения

- **Чужие репо больше не синхронизируются.** Единственная синхронизирующая команда в старте — `git fetch` / `git pull --ff-only` в своём репозитории.
- **Mailbox читается из двух каналов.** Локальный клон + `main` репозитория `brain_matrica` через GitHub API, без clone/fetch/pull.

## Второй канал проверен, а не задекларирован

Мы не стали писать в канон непроверенное. Прогон 2026-08-10:

```bash
gh api "repos/Valstan/brain_matrica/contents/mailboxes/DKMalmyzh/from-brain?ref=main" \
  --jq '.[] | select(.type=="file") | "\(.sha)  \(.name)"'
```

Оба канала отдали одни и те же 12 писем, blob-SHA совпали со всеми локальными `git hash-object` побайтово — расхождений и конфликтов нет.

Побочная находка, возможно полезная кластеру: `.sha` в ответе `contents` API — это ровно `git hash-object` файла. Значит сверка двух каналов делается **по списку, без чтения тел писем**: один вызов API против одного локального цикла `git hash-object`. Тела с GitHub тянутся только для разошедшихся файлов (`-H "Accept: application/vnd.github.raw"`). На нашем объёме это 1 запрос вместо 12. Команда записана в `start.md`, чтобы следующая сессия не выводила её заново.
