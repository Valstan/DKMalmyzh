# Три отчёта, выглядевших успехом

Продолжение сегодняшнего письма про зелёные проверки. Второй заход аудита пошёл по живым данным прода, и там нашлось то, чего чтение кода не давало: три случая, где **инструмент отрапортовал успех, не сделав работу**. Все три — не про наш проект, а про Payload, ssh и оболочку шага.

## 1. Payload: правка ушла в версию, а не в запись

Мы завели разовую операцию — привести адреса импортированных записей к уникальным (об этом ниже). Прогон ответил: «просмотрено 636, переименовано 636, с ошибкой 0». SQL-проба следом показала **те же 49 совпадающих адресов**, что и до прогона.

`payload.update` с `draft: true` кладёт правку в `_posts_v`. Колонка `posts.slug` — та, по которой открывается страница и которую видит SQL, — остаётся прежней. Ни исключения, ни предупреждения.

Симметричная половина: `payload.find` с `draft: true` **читает версии**. Следующий прогон операции прочитал в версиях уже исправленные адреса и ответил «без изменений 636», пока в самой таблице лежали старые. То есть операция дважды отрапортовала успех, ни разу не сделав работу.

Лечение у нас: и писать, и читать основную запись; публикация от этого не включается — состояние берётся из `data._status` ([G223](../../cross-project-ideas/GOTCHAS.md#g223)). И главное — **приёмка по факту**: после каждого обновления документ перечитывается и адрес сверяется, расхождение считается отказом. Без этого шага «обновилось не там» неотличимо от успеха.

**Кому смотреть:** всем на Payload с включёнными drafts, у кого есть служебные операции массового обновления. Это родня G223, но с другой стороны: G223 про то, что `draft: false` не публикует, а здесь `draft: true` пишет мимо того места, куда смотрят все остальные.

## 2. `ssh` не передаёт argv: «сухой» прогон оказался боевым

Воркфлоу ручного запуска передавал операцию, slug и флаг «только показать план» позиционными аргументами: `ssh host 'bash -s' "$OP" "$SLUG" "$DRY"`.

ssh не передаёт массив аргументов. Он **склеивает их в одну строку**, и удалённый шелл разбирает её заново. Пустой аргумент при этом исчезает, а следующие сдвигаются. Запуск с пустым `slug` и `dry_run=true` отдал «true» в `$2` — то есть в slug, — а `$3` остался пустым.

Прогон, задуманный как сухой, отработал боевым и честно написал в ответе `dryRun: false`. Повезло: операция была идемпотентной и записи черновиками, ущерба нет. С операцией удаления повезло бы меньше.

Лечение: `ssh host "OP='$OP' SLUG='$SLUG' DRY='$DRY' bash -s"` — именованными переменными; значения к этому моменту уже проверены по белому списку и форме. Тот же механизм, кстати, объясняет, почему инъекция во входных данных `workflow_dispatch` так опасна: удалённый шелл разбирает строку **второй раз**, и кавычки на раннере от этого не спасают.

## 3. Проба через конвейер не может покраснеть

Обе наши read-only пробы гнали удалённый скрипт так: `ssh … <<'REMOTE' | redact`. Шаг исполняется дефолтной оболочкой GitHub Actions — `bash -e {0}`, **без** `-o pipefail`. Кодом шага становится код `sed`, то есть всегда ноль.

Все аварийные ветки удалённого скрипта — включая «sha256 архива не сошёлся, выгрузка повреждена» — давали зелёный прогон. Наша приёмка выгрузки Калинино держалась на проверке, которая физически не могла провалиться.

Лечение — одна строка: `shell: bash` (даёт `-eo pipefail`). Проверять стоит каждый шаг, где после `ssh`, `curl` или `docker` стоит конвейер: маскировка вывода через `sed` — самый частый случай.

# Что нашлось в наших данных тем же заходом

Не класс, а факт для реестра: у нас на проде лежало **123 записи под 49 одинаковыми адресами** из 636. Slug считался из заголовка, а заголовки импорта из ВК повторяются по построению (два фотоальбома без текста за день, репост одной афиши двумя ДК). Поле не `unique`, страница отдаёт первый попавшийся документ — при публикации порядка 74 материалов оказались бы недоступны при живых ссылках из ленты.

Починено: slug несёт `vkUid`, существующие записи переименованы. Проба после прогона: **дублей 0 из 636**.

И вторая потеря, найденная там же: импорт перезаписывал массив источников ВК только теми ссылками, которые удалось разрезолвить в этот прогон. Ссылка, поймавшая 429 шлюза, исчезала из карточки, как только сосед по массиву обновил свой `ownerId`. У головного РЦКД пара «короткое имя + числовой адрес» — числовой проходит всегда, короткое имя ходит в шлюз. Теперь обходится исходный список.
